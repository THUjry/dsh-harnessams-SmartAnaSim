# AGENTS.md — HarnessAMS-SmartAnaSim

> Rules for AI agents and human maintainers working in this repo. Read this file before changing anything here. This repo keeps English-only, self-contained content (no references to files outside the repo).

- Package `dsh-harnessams-smart-ana-sim` / row id `harnessams-smart-ana-sim`, version 0.1.0; `engines.dsh` locks the verified DSH version. The plugin has **no runtime `@deepseek-ai/dsh-*` dependency**: tool definitions are built by the local schema compiler in `src/tool.js` (see "Tool schema" below). Sole dependency (runtime `dependencies`, 2026-11-01): `@deepseek-ai/schemastery` for the Config family toggles — installed bundles do not get devDependencies and schemastery is not a host-provided peer, so peer+dev would fail to resolve in installed form (same placement rule the retired `dsh-remote` used; `tests/entry.test.mjs` guards it).
- **Positioning (2026-11-23 ruling)**: this package is a PURE TOOL SET, usable on its own — no other plugin required, and no reference to any other plugin's tools in tool descriptions, file headers or skill text. The spectre side is limited to template generation + configuration checks; sweep execution and result parsing are script-face (data processing is not tool-shaped); the managed scan flow (submission, monitoring, result retrieval) lives in the HarnessAMS suite's batch channel, which drives this package's workers through the workspace `sim_scripts_dir`.
- **Tool surface (6)**: `spectre_assemble`; `snp_guide` (always declared) + `snp_read` / `snp_extract` (deferred, guide-gated — see the snp_* bullet); `gen_vsch_import` / `gen_vsch_export` (Virtuoso schematic interaction, see the vsch bullet). The `spectre_run_sweep` / `spectre_parse` tools were retired on 2026-11-23 (their capability is the scripts + the skill; 0.1.0 was never published, no aliases). The ngspice family was removed on 2026-11-02 (pre-removal state: this repo's `ngspice` branch).
- **vsch family (2026-11-23)**: `gen_vsch_import` / `gen_vsch_export` assemble ready-to-run TEXT for the netlist <-> OpenAccess round trip — pure JS string assembly in `src/tools/vsch.js`, never executes anything, never writes files (cds.lib layout / install roots / license hosts are environment-specific; execution belongs to the caller). Each returns structured schemes (`param`/`cli`/`plain_skill` for import, `si`/`ocean`/`cdlout`/`plain_skill` for export); `plain_skill` = self-contained Cadence SKILL text pasteable into an open CIW, doubling as the F1 fallback when a headless carrier fails. Recipes live in the skill pages `virtuoso-import.md` / `virtuoso-export.md` (migrated in full from the project's 2026-11-23 Virtuoso-interaction research; the research doc was deleted after migration).
- **Wording rule (2026-11-23)**: "SKILL language" / "SKILL script" always means the Cadence SKILL language — the language itself, never necessarily a file on disk; lowercase `skill` or the bare word means a DSH plugin skill (like the bundled `smart-spectre`). Applies to README, docs, tool descriptions and skill text.
- **Markdown style rule (2026-11-24)**: every `.md` file keeps one paragraph per line — no manual hard-wrapping inside a paragraph (repo-wide: README, PUBLISH, docs, bundled skill pages included). Exempt from merging: YAML frontmatter, fenced code blocks, tables, list-marker lines, and intentionally indented command blocks.
- **Bundled skill**: `skills/smart-spectre/` — root `SKILL.md` (scope: pure command-line simulation + parameter sweeps; index + the Virtuoso round-trip pointer + the bridge-lite external pointer) plus companion pages `spectre-cli.md` (the operational page: direct runs, assembly layer, run-directory contract, sweep worker + sweep_config schema, psf analysis script, cascade assembly; snp_* tools are out of scope), `spectre-grammar.md` (netlist syntax with a section per analysis type: template `@@PARAM@@` rules, Spectre-vs-SPICE rules and units, AC excitation, sp with `paramtype=yz`, swept PSS configuration), `virtuoso-import.md` (netlist -> OA, incl. the round-trip charter) and `virtuoso-export.md` (OA -> netlist). The `skill` tool renders the body with a base-directory hint but never enumerates the directory — the root page must name every companion file explicitly (`tests/entry.test.mjs` pins the gate). Registration is fail-open via `src/skills.js` (`resourceBase` = the skill dir); `inject` carries `'skills'` (cordis blocks undeclared ctx services).
- **Layout**: plugin source under `src/` (entry `src/index.js`, plain JS, no build chain), the bundled skill under `skills/smart-spectre/`, runtime Python under `scripts/{common,spectre,snp}/`, the numpy-fallback backend under `assets/`, tests under `tests/` (bare `node --test` from the repo root; a directory argument fails on Node 24). Every script filename carries its family prefix (`common_*`, `spectre_*`, `snp_*`); keep it that way even inside subdirectories, and keep the unique basenames (a flat remote upload must not collide).
- **Script layer**: scripts are plain files spawned by the Node channel (`python <script> …`). Cross-directory imports insert `scripts/` (the parent of the script's own directory) into `sys.path` and use `from common.common_sweep_engine import …` / `from spectre.spectre_psf_parse import …`. No `__init__.py` (PEP 420 namespace packages). Assembly/check/adjudication logic lives entirely in the script layer; the Node side is a channel only.
- **Language rule** (suite-wide, D-003 in the HarnessAMS repo's `docs/decisions.md`): in-plugin functionality is JS single-implementation by default; this package's Python is confined to the three sanctioned families — sweep workers (e.g. `spectre_sweep_worker.py`), s-parameter numeric computing (e.g. `snp_extract.py`), and per-project user-authored assembly scripts (e.g. `gen_selfcheck_rc.py`, shipped by the top-level plugin's self-check project) — no new Python families beyond these.
- **Shared sweep engine** (`scripts/common/common_sweep_engine.py`): `@@PARAM@@` substitution, cross-product/zip combinations, point directories (`00`, `01`, …; plain decimal from 100), atomic `point_meta.json`, `sweep_progress.json` on a 30 s cadence, `.worker_started` / `.compute_node` / `.simulator` markers. Every sweep worker must keep this data contract; simulator-specific command execution and output parsing stay in each worker.
- **Tool schema**: `src/tool.js` compiles the author-facing parameter DSL into an object-rooted JSON Schema. `required` may only be `true` (omit it for optional). The old `required: false` form was the root cause of the `type: null` schema bug (dev-mount could not resolve `@deepseek-ai/dsh-tools` and registered the raw DSL); do not reintroduce it. A def may also carry `deferLoading: true` (forwarded onto the compiled tool, literal true only) and a `when` admission predicate (forwarded as `ctx.tools.register` options; kept out of the compiled tool object). `entry.test.mjs` asserts every tool's schema, required list, enum and output shape.
- **Family toggles (2026-11-01)**: `src/index.js` exports a schemastery `Config` (`spectre`/`snp` booleans, default `true`; changing the config hot-swaps the plugin — cordis restarts the fiber and re-registers). DSH (0.2.1-rc.2; 0.2.2-rc.1 source-checked 2026-11-10, unchanged) does NOT auto-render a bundle's config as settings-page switches: the plugin manager shows them only when the bundle's browser half registers the `plugins.row.config` slot (key `<package>#<row id>`); this package ships no browser half (deferred by user decision 2026-11-01), so the toggles are edited through the profile config layer. `toolDefinitions(ctx, config)` trims a family only on explicit `false` (`!== false`, so `undefined` never trims); the `~standard` validate hook must stay a real schemastery schema — cordis `resolveConfig` calls it directly on the exported object and a plain object crashes the load. The official `tool-fs` plugin (read/write/edit booleans) is the pattern precedent.
- **Spectre channel**: `spectre_assemble` runs the project's `gen_*.py` (cwd = project root, `--out` forwarded, `HARNESSAMS_SIMULATOR=spectre` in the env, `DSH_SESSION_ID` threading the per-session check table). Worker contract: psfascii output (`output_format: "psfascii"`), `template*.scs` (default `template.scs`; the name must match `sweep_config.netlist_template`), `@@PARAM@@`; command defaults `+lqtimeout 900`, `-maxw 5`, `-maxn 5`, `++aps` (never `+preset aps`; SPECTRE-132), `+mt`, `+logstatus`; smart timeout extends once for `Waiting for available license` and once for raw output before killing. Statuses: success (rc 0), partial (rc!=0 with raw output), failure (rc!=0 without), timeout (killed), error (spawn/template). `spectre_psf_parse.py` handles PSF ASCII (swept/delta/complex/non-swept info) plus S-parameter `sp.sp` (delegated to `snp_common.parse_psfascii`, flattened to `freq` + `s11..sNN` complex curves; `--raw-dir` may point directly at a standalone `.sp` file); binary PSF is unsupported by design. `spectre_checks.py` owns the `.scs` assembly checks, including the geometry unit-suffix rule (bare number = metres in Spectre) and the ideal R/C/L value-range gate (R 0.1..1M ohm, C 1f..1u farad, L 0.1p..10n henry, inclusive; literals, `@@P@@` swept values and template `parameters` references; `m`/`M` follow Spectre case sensitivity).
- **snp_***: S-parameter reading/extraction, tools-only (no UI). Purpose (stated 2026-11-21): convert S-parameter data to CSV for convenient calculation and extract passive-device parameters. **snp_extract takes the params CSV only (2026-11-23)**: raw `.sNp` / `sp.sp` inputs exit 2 with a convert-first hint; `snp_read` remains the three-format converter and its params CSV round trip is bit-exact (`%.17g` — 12 digits once flipped the coupled_tl eigenvalue branch and the auto port search on the scrambled fixture). **Guide-gated deferred loading (2026-11-18)**: only `snp_guide` is always declared; `snp_read`/`snp_extract` register `deferLoading: true` + a `when` predicate over a module-level `Set` of agent ids that called the guide (`src/tools/snp.js`). On `toolUpdate` routes (deepseek-flash default) activation rides `tool-addition` and preserves the KV-cache prefix; on routes without it `deferLoading` is stripped and activation resends declarations (one-time prefix break). Activation is one-way (never unset — addition-only routes drop removals), keyed by agent id string so in-process session restore keeps it; after a server restart the model self-heals by re-calling the guide; sub-agents call the guide themselves. The guide marks activation only inside its execute (a tool call is inherently after the session's first request — required, or the deferred tools land in the declaration baseline and never activate). Wire-verified on a live 0.2.2-rc.3 instance 2026-11-18. The registry validates execute() results against `output.schema` — a string-returning guide needs an explicit string-schema `output` override on the def (fix a8fbf42; the object-rooted default rejects strings with `"value" must be an object`). Numeric backend: numpy primary, `assets/numfallback.py` automatic pure-stdlib fallback (`SNP_FORCE_FALLBACK=1` forces it); both backends share the same upper-level code and must agree (test-asserted). Touchstone v1 ordering: 2-port files are S11,S21,S12,S22; N>2 files are row-major. The coupled_tl theory gate (default 5.0e-2) is calibrated at 4x the validated reference coupler's relative off-block residual; changing it requires recalibration notes. Known port-mapping trap: a through-pair grouping block-diagonalizes perfectly but yields non-physical modal impedances / split thetas — the physicality checks (Re(Z0) resistive-dominant, theta monotonic, theta_e ~= theta_o) must stay.
- **Hard PDK isolation**: PDK paths live only in assembly-layer configuration, never in agent context; the format / dimension / ideal-value-range / bias<Vdd checks reject at the assembly layer, before the simulator. The assembly layer is the only code path that touches PDK files.
- **Workspace convention (D-004, 2026-11-19)**: the family `harnessams.json` walker is RETIRED — configuration now lives per project at `<project>/.harnessams/workspace_config.json`, and nothing reads `harnessams.json` anymore (`common_workspace.py` keeps only a retirement note where the walker used to be). This package's remaining config face is `spectre_cmd`, resolved as the `--spectre-cmd` argument > the run's `sweep_config.json` `spectre_cmd` > `PATH`. `pdk_lib` never had a consumer here (PDK paths live in assembly-layer configuration only); the project's `workspace.sim_scripts_dir` still points at this package's `scripts/` tree (the suite's batch upload tree depends on it).
- **Tests**: `node --test` from the repo root (35 tests) covers tool metadata/schema/validation (including the deferred-registration shape, the guide activation semantics and the bundled-skill naming gate), recursive script parsing + filename prefixes, PSF parsing (`tests/data/psf`), the Spectre worker mechanics with a fake process layer (`tests/spectre_worker_test.py`), the assembly checks including the ideal RCL ranges (`tests/spectre_checks_test.py`), the S-parameter regression suite (`tests/data`, chained read-then-extract) and the JS tool-face contracts (snp summary/exit-1). Python self-tests run as plain scripts and use `python -B` so they never write `__pycache__` into the repo. `tests/manual/compare_spectre_runs.py` is the node1 foreground-vs-batch acceptance helper (not shipped).
